GuardSaaB Architecture & System Reference Manual

GuardSaaB is a local-first AI agent security control plane. It functions as an external, deterministic pre-execution gatekeeper for autonomous developer agents (Claude Code, Codex CLI, Cursor, Cline). It intercepts tool invocations prior to execution, evaluates multi-layered declarative policies, calculates contextual risk, and holds high-impact actions for human authorization.

This manual serves as the technical single source of truth for the product. Every component, decision pathway, database trigger, and limitation described herein maps 1:1 to verified code in this repository.

ALLOW action=ALLOW

Command or tool passes all policy rules and presents low risk. Returned immediately to agent client; executes without human interruption.

AUDIT action=ALLOW (Flagged)

Tool is unblocked so developers stay productive, but the call is flagged with high audit priority in the tamper-evident chain for compliance review.

HITL (Ask) action=HELD (TTL: 120s)

Socket is held open. The call appears in the GuardSaaB Console approval queue. Fails closed (blocks) if timeout expires without human approval.

BLOCK action=BLOCK

Violates mandatory deny rules (destructive deletions, credential theft, sensitive directories). Gateway denies request and explains reason.

Core Subsystems

Detailed Architecture Specifications

1. Deterministic Policy Engine

Unlike probabilistic LLM guardrails that hallucinate under load, GuardSaaB uses deterministic JsonLogic loaded from YAML.

Every rule specifies explicit precedence: mandatory block rules (destructive syntax, `.env`, private keys) execute first and cannot be overridden by risk score or prompt nuances.

File: src/policy/jsonlogic.ts

2. Merkle Cryptographic Audit

Audit events are stored in PostgreSQL table guardsaab_audit_chain. Each row computes a SHA-256 digest over sequence, timestamp, payload, and the rolling previous_hash.

PostgreSQL triggers reject any SQL UPDATE or DELETE statements, creating an append-only verifiable cryptographic ledger.

File: src/db/audit-store.ts

3. Dual Portal State Boundary

The engine simultaneously hosts two isolated frontends:

Northstar Works (:5173): Simulates an enterprise workplace with employee directory, fund requests, and Zeo AI assistant.
GuardSaaB Console (:5174): Central governance cockpit monitoring telemetry, session replays, and approvals.

File: dashboard/src/App.tsx & CompanyWorkspace.tsx

Architectural Roadmap

Hardening GuardSaaB for Production Deployment

01 Kernel-Level Enforcement (eBPF & Landlock)

Problem: Application-layer hooks rely on agent cooperation. A malicious or confused agent could unset environment variables or spawn child processes directly.

Solution: Enclose agent execution in Linux Landlock / eBPF syscall filters or micro-VMs (Firecracker / gVisor). Any unauthorized file modification or network socket is blocked by the kernel regardless of hook status.

02 Post-Tool Execution Attestation & Diffing

Problem: Current tool hooks fire exclusively before execution (PreToolUse); GuardSaaB does not verify what the command actually produced.

Solution: Implement mandatory PostToolUse attestation that records exit codes, stdout hashes, and git filesystem diffs to prove command integrity.

03 Cryptographic Workload Identity (SPIFFE/mTLS)

Problem: Agent calls are keyed by ephemeral session IDs or working directory paths.

Solution: Issue short-lived X.509 SVID certificates to agent runtimes via SPIFFE/SPIRE, ensuring every tool call carries cryptographic proof of the agent's identity and codebase revision.

04 Hardware-Anchored Timestamping (RFC 3161)

Problem: Audit signing keys reside locally on the host machine.

Solution: Publish periodic Merkle root digests to an external RFC 3161 Timestamping Authority or Cloud KMS, establishing mathematical tamper-evidence even against a host administrator.
